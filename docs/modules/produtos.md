# Módulo: Produtos

> **Evolução em andamento (DEC-030):** o cadastro de produtos está sendo ampliado em 6 fases (A–F). Itens que esta spec lista como fora do escopo — categorias e unidades como cadastros, múltiplos códigos de barras, promoções/atacado e estoque com movimentações — passam a fazer parte do escopo por decisão do usuário. **Fase A concluída** ([categorias-e-unidades.md](categorias-e-unidades.md)): `categoria` e `unidade` deixaram de ser texto — o produto referencia `unidade_id` (obrigatório), `categoria_id` (opcional, qualquer nível da árvore), `unidade_compra_id` + `fator_conversao` (migration V6); a API recebe `unidadeId`/`categoriaId`/`unidadeCompraId`/`fatorConversao` e devolve `unidade`/`categoria`/`unidadeCompra` como objetos e `conversaoTexto`. Onde esta spec fala em `categoria`/`unidade` como texto, vale o modelo novo. **Fase B concluída** ([produtos-identificacao-e-formulario.md](produtos-identificacao-e-formulario.md), migration V7):
- vários códigos de barras em `produto_codigos_barras`, com validação EAN/UPC; o campo único `codigoBarras` deixou de existir;
- nome curto, fornecedor principal e SKU sugerido;
- exclusão física de produto que nunca movimentou;
- **UUID público** nas rotas;
- cadastro em página própria com abas.

As colunas de texto antigas `categoria`, `unidade` e `codigo_barras` foram removidas. Fiscal continua fora.

## 1. Visão geral

Produto é o item físico que um pequeno negócio vende. É a entidade central que conecta PDV, estoque, financeiro e relatórios: sem produto cadastrado, não há venda, não há movimentação de estoque e não há receita a registrar.

Inicialmente o Geitus trabalha **apenas com produtos físicos**. Serviços (ex.: banho e tosa, montagem) ficam fora do MVP e serão tratados futuramente em módulo ou aba separada.

**Limites do MVP:** cadastro simples, busca eficiente para o PDV, e uma base de dados preparada para o módulo de Estoque — sem funcionalidades avançadas de precificação, variação ou fiscal.

## 2. Objetivos do módulo

- Permitir cadastro e manutenção de produtos físicos.
- Facilitar a busca de produtos no PDV (por nome, SKU ou código de barras).
- Preparar a base de dados para o módulo de Estoque básico (movimentações futuras).
- Evitar duplicidade e inconsistência de cadastro (SKU e código de barras únicos por empresa).

## 3. Fora do escopo do MVP

- Serviços (ex.: banho e tosa, montagem, consertos).
- Agendamento.
- Controle de validade.
- Controle de lotes.
- Grade avançada de roupas (tamanho/cor como variações estruturadas).
- Múltiplos estoques (por loja/depósito).
- Tabela de preços avançada (preços por canal, por cliente, promoções).
- Variações complexas de produto (kits, combos).
- Integrações fiscais (NF-e, NFC-e).
- Integrações externas (marketplaces, e-commerce).
- Importação em massa (planilha, API).
- Histórico avançado de alteração de preço/custo — previsto para o futuro (ver seção 10), não implementado nesta especificação.

## 4. Modelo conceitual inicial

> Conceitual — não define migration nem nomes técnicos finais. A modelagem definitiva será feita na etapa de implementação backend.

Campo | Tipo (conceitual) | Observações
---|---|---
`id` | `Long` / `BIGINT` | Identidade interna, seguindo o padrão já decidido do projeto (DEC-015: `BIGINT GENERATED BY DEFAULT AS IDENTITY`).
`empresaId` | `Long` | Isola o produto por empresa/tenant, seguindo o mesmo padrão já usado em Usuário (DEC-016). Todo produto pertence a exatamente uma empresa.
`nome` | texto | Obrigatório.
`categoria` | texto | Campo essencial inicial; agrupamento simples, sem hierarquia complexa no MVP.
`unidade` | texto | Ex.: "un", "kg", "cx". Sem cadastro de unidades de conversão no MVP.
`precoVenda` | decimal | Obrigatório; valor monetário (o backend deve usar tipo decimal exato, nunca ponto flutuante, quando implementado).
`custo` | decimal | Opcional.
`estoqueMinimo` | decimal/inteiro | Opcional; usado futuramente para alertas do módulo Estoque.
`codigoBarras` | texto | Opcional; único por empresa quando informado.
`sku` | texto | Opcional; único por empresa quando informado.
`ativo` | booleano | Status ativo/inativo.
`criadoEm` / `atualizadoEm` | data/hora | Auditoria mínima, no mesmo padrão de Empresa/Usuário.

**Observação sobre estoque:** não existe campo de "estoque atual" neste modelo conceitual. O estoque atual **não deve ser armazenado nem editado diretamente**; ele deve ser **derivado de movimentações** quando o módulo Estoque básico for implementado. Um "estoque inicial" pode existir futuramente como uma entrada operacional (ou seja, a primeira movimentação de entrada), não como um campo editável do cadastro de produto.

### Modelo de dados atual (implementado — tabela `produtos` no baseline `V1__baseline.sql`)

> A tabela `produtos` foi um dos primeiros módulos do projeto e, na consolidação do baseline (**DEC-020**), seu DDL foi absorvido pelo `V1__baseline.sql` (não existe um `V3__produtos.sql` — o `V3` atual é `V3__empresa_cadastro.sql`). Fonte do schema: `backend/src/main/resources/db/migration/V1__baseline.sql`.

Tabela `produtos`:

| Coluna | Tipo | Observações |
|---|---|---|
| `id` | `BIGINT` identity | PK (DEC-015) |
| `empresa_id` | `BIGINT` | NOT NULL, FK → `empresa(id)`, com índice (DEC-016) |
| `nome` | `VARCHAR(150)` | NOT NULL |
| `categoria` | `VARCHAR(100)` | |
| `unidade` | `VARCHAR(20)` | |
| `preco_venda` | `NUMERIC(12,2)` | NOT NULL, CHECK `>= 0` |
| `custo` | `NUMERIC(12,2)` | CHECK `>= 0` quando informado |
| `estoque_minimo` | `NUMERIC(12,3)` | 3 casas para unidades fracionárias (kg/litro); CHECK `>= 0` |
| `codigo_barras` | `VARCHAR(50)` | único por empresa (`UNIQUE (empresa_id, codigo_barras)`) |
| `sku` | `VARCHAR(50)` | único por empresa (`UNIQUE (empresa_id, sku)`) |
| `marca` | `VARCHAR(100)` | opcional; texto (não é entidade). **V4** (DEC-028) |
| `descricao` | `VARCHAR(1000)` | opcional; descrição/observações livres. **V4** (DEC-028) |
| `estoque_maximo` | `NUMERIC(12,3)` | opcional; CHECK `>= 0`; hint p/ o futuro Estoque. **V4** (DEC-028) |
| `ponto_reposicao` | `NUMERIC(12,3)` | opcional; CHECK `>= 0`; hint p/ o futuro Estoque. **V4** (DEC-028) |
| `preco_minimo` | `NUMERIC(12,2)` | opcional; CHECK `>= 0`; piso de venda. **V4** (DEC-028) |
| `ativo` | `BOOLEAN` | NOT NULL, default `true` |
| `criado_em` / `atualizado_em` | `TIMESTAMP` | mesmo padrão de empresa/usuário |

> **Incremento cadastral (migration `V4__produtos_incremento_cadastral.sql`, DEC-028):** as colunas `marca`, `descricao`, `estoque_maximo`, `ponto_reposicao` e `preco_minimo` foram acrescentadas de forma **aditiva** (todas nullable; V1/V2/V3 intactas), alinhando o Produto à modelagem do PDV sem trazer fiscal, variações, lote/série ou multi-estoque.

Strings vazias de SKU/código de barras — e agora também de `marca`/`descricao` — são normalizadas para `NULL` no service (múltiplos `NULL` não conflitam na constraint UNIQUE do Postgres).

**Campos derivados (não são colunas):** a `ProdutoResponse` calcula, quando há custo, **`markup`** = (preço − custo) / custo × 100 (marcação sobre o custo; `null` quando `custo` ausente ou `0`) e **`margem`** = (preço − custo) / preço × 100 (margem sobre a venda; `null` quando `custo` ausente). Ambos com 2 casas (HALF_UP). Alinha ao princípio "calcular automaticamente".

### Endpoints implementados (autenticados)

Todos derivam a empresa do usuário autenticado (JWT); nenhum aceita `empresaId` por path, query ou body.

| Endpoint | Descrição | Respostas |
|---|---|---|
| `GET /api/produtos` | Lista produtos da empresa; filtros opcionais `busca` (nome, SKU ou código de barras, sem diferenciar maiúsculas) e `ativo` (`true`/`false`) | 200 |
| `GET /api/produtos/{id}` | Busca por id dentro da empresa | 200 / 404 |
| `POST /api/produtos` | Cadastra produto (**ADMIN**) | 201 / 400 / 403 / 409 |
| `PATCH /api/produtos/{id}` | Atualiza dados básicos (**ADMIN**) | 200 / 400 / 403 / 404 / 409 |
| `PATCH /api/produtos/{id}/inativar` | Inativa o produto (**ADMIN**) | 200 / 403 / 404 |
| `PATCH /api/produtos/{id}/reativar` | Reativa o produto (**ADMIN**) | 200 / 403 / 404 |

- **RBAC (DEC-025):** **escrita** (POST/PATCH — cadastrar, atualizar, inativar, reativar) exige **ADMIN**; **leitura** (GET) é livre a qualquer autenticado. OPERADOR vê o catálogo, mas não o altera (backend → 403; frontend em modo leitura).
- Produto inexistente **ou de outra empresa** → 404 (mesma resposta, sem revelar existência entre tenants).
- **SKU ou código de barras duplicado na empresa → 409** (conflito de unicidade, padronizado com CNPJ/e-mail — DEC-026); validação de campos (nome/preço/custo/estoque) → 400 com `campos`.
- Sem token → 401. Não há `DELETE` (inativação é o caminho padrão).
- A resposta (`ProdutoResponse`) não expõe `empresaId` nem a entidade JPA.

No frontend, a página protegida `/produtos` consome esses endpoints (listagem com busca/filtro, cadastro, edição, inativação e reativação).

## 5. Regras de negócio iniciais

- Produto deve pertencer a uma empresa (`empresaId` obrigatório).
- Nome é obrigatório.
- Preço de venda é obrigatório.
- Preço de venda não pode ser negativo.
- Custo, se informado, não pode ser negativo.
- Estoque mínimo, se informado, não pode ser negativo.
- Estoque máximo, ponto de reposição e preço mínimo, se informados, não podem ser negativos.
- **Coerência (DEC-028):** quando ambos informados, `preco_minimo` ≤ `preco_venda` e `estoque_maximo` ≥ `estoque_minimo` (igualdade permitida); violação → 400. Validado no service (não como CHECK de banco, para não engessar).
- SKU deve ser único **por empresa** quando informado.
- Código de barras deve ser único **por empresa** quando informado.
- Produto pode ser ativado/inativado.
- Produto inativo não deve aparecer para venda no PDV.
- Produto inativo pode continuar aparecendo em relatórios históricos (vendas passadas não desaparecem).
- Produto vendido não deve ser excluído fisicamente.
- Produto com movimentação de estoque (quando o módulo existir) não deve ser excluído fisicamente.
- Exclusão física não é prioridade do MVP — inativação é o mecanismo preferido, alinhado à regra geral do `CLAUDE.md` de evitar exclusão física de dados importantes.
- Atualizações de preço/custo devem preservar consistência do cadastro; histórico dessas alterações poderá ser implementado futuramente (fora do escopo agora).

## 6. Regras de UX

- Cadastro simples e rápido — priorizar os campos essenciais.
- Campos essenciais aparecem primeiro; campos avançados ficam ocultos/agrupados.
- Evitar tela poluída.
- Feedback claro ao salvar, editar, inativar ou quando ocorrer erro.
- Marca junto dos campos comuns; custo, estoque (máx/mín/reposição), preço mínimo e descrição agrupados no bloco avançado.
- Margem/markup exibidos de forma derivada (só-leitura) quando há custo — o sistema calcula, não pede.
- Busca por nome, SKU e código de barras.
- Ações frequentes (buscar, cadastrar, inativar) com o menor número possível de cliques.
- Não obrigar informações que o pequeno negócio talvez ainda não tenha (ex.: código de barras, SKU são opcionais).
- Indicar visualmente o status ativo/inativo.
- A base de dados e a busca devem estar preparadas para o uso rápido exigido pelo PDV (ver `CLAUDE.md`, diretriz do módulo PDV).

## 7. Casos de uso iniciais

- Listar produtos.
- Buscar produto por nome, SKU ou código de barras.
- Cadastrar produto.
- Editar produto.
- Inativar produto.
- Reativar produto.
- Consultar detalhes do produto.

## 8. Critérios de aceite para implementação futura

### Backend futuro

- CRUD protegido por autenticação; **escrita exige ADMIN, leitura livre** (DEC-025).
- Produtos sempre filtrados pela empresa do usuário autenticado (mesmo padrão de isolamento já usado em `/api/empresas/minha`, ver [docs/modules/empresa.md](empresa.md)).
- Nenhum endpoint deve receber `empresaId` como parâmetro para acessar dados de outra empresa — a empresa é sempre derivada do usuário autenticado.
- Validações no backend (nome obrigatório, preço de venda obrigatório e não negativo, custo/estoque mínimo não negativos quando informados).
- Testes de isolamento por empresa (um usuário não deve enxergar/alterar produto de outra empresa).
- Testes de unicidade por empresa para SKU e código de barras.

### Frontend futuro

- Página protegida de produtos.
- Lista com busca.
- Formulário com validação (React Hook Form + Zod, seguindo o padrão já usado em Empresa/Login).
- Estados de loading, erro, vazio e sucesso.
- Feedback claro após salvar/inativar.
- Layout consistente com o restante do Geitus (mesmos componentes shadcn/ui, mesma linguagem visual).

## 9. Relação com módulos futuros

- **PDV:** busca e venda de produtos ativos.
- **Estoque:** movimentações de entrada/saída e cálculo do estoque atual a partir delas.
- **Caixa:** vendas de produtos impactam o caixa do período.
- **Financeiro:** vendas geram receitas.
- **Relatórios:** produtos vendidos, margem, produtos abaixo do estoque mínimo.

## 10. Decisões e pendências

**Decidido agora:**
- Produto é sempre físico neste momento; serviços ficam fora do MVP.
- Produto pertence a uma única empresa (`empresaId`), seguindo o mesmo padrão de isolamento de Empresa/Usuário (DEC-015, DEC-016).
- Estoque atual não é um campo do cadastro de produto; será sempre derivado de movimentações no módulo Estoque.
- SKU e código de barras são opcionais, mas únicos por empresa quando informados.
- Exclusão física não é prioridade; inativação é o mecanismo padrão.
- **Migration e nomes técnicos das colunas** definidos: a tabela `produtos` vive no `V1__baseline.sql` (consolidação DEC-020); precisão monetária com tipo decimal exato (`NUMERIC(12,2)` / `BigDecimal`).
- **RBAC (DEC-025):** escrita (cadastrar/atualizar/inativar/reativar) exige ADMIN; leitura livre a qualquer autenticado.
- **Conflito de unicidade (DEC-026):** SKU/código de barras duplicado retorna 409 (padronizado com CNPJ/e-mail).
- **Testes de integração (DEC-027):** queries de repositório cobertas por Testcontainers (`ProdutoRepositoryIT`) contra Postgres real.

**Deixar para depois:**
- Histórico de alteração de preço/custo.
- Categorias como entidade própria (hoje é apenas um campo texto) — avaliar se vira tabela própria quando houver necessidade real.

**Fora do escopo:**
- Serviços, agendamento, banho e tosa.
- Controle de validade e de lotes.
- Grade avançada de roupas.
- Múltiplos estoques.
- Tabela de preços avançada e variações complexas (kits/combos).
- Integrações fiscais e externas, importação em massa.
