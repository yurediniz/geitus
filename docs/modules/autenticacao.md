# Módulo: Autenticação

## Objetivo

Permitir que usuários de um pequeno negócio acessem o Geitus de forma segura, com login por e-mail e senha, emissão de token JWT e proteção das rotas da aplicação. É a base sobre a qual os demais módulos (produtos, clientes, PDV, caixa, financeiro) exigirão um usuário autenticado.

## Escopo (Etapa 5 — autenticação inicial)

- Login por e-mail e senha (`POST /api/auth/login`).
- Senha armazenada com hash **BCrypt** (nunca em texto puro).
- Emissão e validação de **JWT (HS256)**, política **stateless**.
- Consulta do usuário autenticado (`GET /api/auth/me`).
- Proteção de rotas no backend (tudo autenticado, exceto rotas públicas explícitas).
- Estrutura **mínima** de empresa/tenant para sustentar o vínculo do usuário (DEC-016).
- Tela de login no frontend, separação entre rotas públicas e privadas, e logout simples.
- Documentação da API via OpenAPI/Swagger em desenvolvimento (DEC-012).

## Fora do escopo

- Refresh token e revalidação automática de sessão.
- Recuperação/redefinição de senha.
- MFA/2FA, OAuth/SSO.
- RBAC avançado (permissões granulares por perfil).
- Rate limiting e lockout de login.
- CRUD completo de usuários e módulo Empresa completo.
- Multiempresa avançado.

## Decisões relacionadas (decision-log)

- **DEC-012** — OpenAPI/Swagger via springdoc-openapi (documenta a API; não substitui esta doc; não expor em produção sem decisão futura).
- **DEC-015** — PK interna `BIGINT GENERATED BY DEFAULT AS IDENTITY` / `Long`.
- **DEC-016** — Usuário nasce vinculado a empresa/tenant (`empresa_id` obrigatório), sem multiempresa avançado nem módulo Empresa completo.

## Endpoints

### `POST /api/auth/login` (público)

Request:

```json
{ "email": "admin@geitus.dev", "senha": "sua-senha" }
```

Respostas:

- **200** — `{ "token": "<jwt>", "usuario": { "id", "nome", "email", "perfil", "empresa" } }`, onde `empresa` contém dados básicos da empresa vinculada.
- **401** — credencial inválida (senha errada, usuário inexistente **ou** inativo) → mensagem genérica `"Credenciais inválidas."` (não revela se o e-mail existe).
- **400** — validação (campos vazios / e-mail inválido), com a lista de `campos`.

### `GET /api/auth/me` (autenticado)

- Header `Authorization: Bearer <jwt>`.
- **200** — `{ "id", "nome", "email", "perfil", "empresa" }` (nunca retorna `senha_hash`).
- **401** — sem token, token expirado, adulterado, com assinatura inválida, ou usuário inativado.

### Rotas públicas mantidas

`GET /api/health`, `GET /actuator/health(/**)`, `POST /api/auth/login` e os caminhos do Swagger (apenas em desenvolvimento). Todo o restante exige JWT válido.

## Regras de segurança

- Senha sempre via **BCrypt**; `senha_hash` nunca aparece em DTO/resposta/log.
- Login **uniforme**: senha errada, usuário inexistente e usuário inativo produzem o mesmo 401 genérico (evita enumeração de e-mails).
- **JWT HS256**, assinatura e expiração validadas; token inválido/expirado/adulterado → 401. Claims mínimos (`subject`=id, `perfil`, `empresaId`), sem dados sensíveis.
- **Fail-fast do segredo**: a aplicação não sobe se `JWT_SECRET` estiver ausente ou tiver menos de 32 bytes (256 bits) para HS256.
- Política **stateless**; CSRF desabilitado (sem sessão por cookie); `httpBasic`/`formLogin` desabilitados.
- **CORS** restrito: `allowCredentials(false)`, origens por variável de ambiente, headers limitados a `Authorization`, `Content-Type`, `Accept`.
- Erros padronizados via `ApiError` (401/403/400), **sem** stack trace, nome de classe ou detalhe interno.
- Nenhum segredo versionado; `.env` ignorado pelo Git; `.env.example` apenas com valores fictícios.

## Regras de UX

- Tela `/login` limpa, centralizada, **sem sidebar**, alinhada à identidade do Geitus.
- Feedback de **loading** no submit (botão desabilitado + indicador).
- Mensagem de erro **humana** para credenciais inválidas (ex.: "E-mail ou senha inválidos."), sem detalhe técnico; mensagem específica para falha de conexão.
- Validação clara por campo (React Hook Form + Zod), com acessibilidade básica (labels, `aria-invalid`, `aria-describedby`, `role="alert"`).
- Rotas privadas redirecionam usuário não autenticado para `/login`; usuário autenticado que acessa `/login` é levado à área principal.
- **Logout** simples (limpa sessão e volta para `/login`); 401 em chamada autenticada limpa o token e redireciona.
- **Carregando sessão (reidratação no boot):** com token salvo, o usuário é revalidado via `GET /api/auth/me` antes de os guards (`ProtectedRoute`/`PublicOnlyRoute`) decidirem o redirect. Enquanto isso, um indicador discreto de carregamento é exibido, evitando o flicker da área privada sem dados do usuário e o "piscar" do login antes de detectar token inválido.

## Variáveis de ambiente

Todas com valores **fictícios** no `.env.example` (nunca segredos reais).

| Variável | Descrição |
|---|---|
| `JWT_SECRET` | Segredo do JWT (HS256). **Obrigatório**: mínimo 32 bytes / 256 bits, senão a aplicação não sobe. |
| `JWT_EXPIRATION` | Expiração do token em milissegundos (padrão 86400000 = 24h). |
| `GEITUS_BOOTSTRAP_DEV_ADMIN` | Habilita o bootstrap do admin de desenvolvimento quando `true` (mapeada para a property `geitus.bootstrap.dev-admin`). |
| `GEITUS_DEV_ADMIN_EMAIL` | E-mail do admin de desenvolvimento. |
| `GEITUS_DEV_ADMIN_PASSWORD` | Senha do admin (usada apenas para gerar o hash BCrypt). |
| `GEITUS_DEV_ADMIN_NAME` | Nome do admin. |
| `GEITUS_DEV_COMPANY_NAME` | Nome da empresa (tenant) criada para o admin. |
| `VITE_API_BASE_URL` | (frontend) URL base da API. |

## Usuário inicial de desenvolvimento

Não há usuário padrão com senha fixa no código. Em desenvolvimento, o **bootstrap idempotente** cria (se ainda não existirem) uma empresa e um usuário admin quando habilitado por variável de ambiente:

```bash
export JWT_SECRET="um-segredo-forte-com-no-minimo-32-bytes-aqui"
export GEITUS_BOOTSTRAP_DEV_ADMIN=true
export GEITUS_DEV_ADMIN_EMAIL="admin@geitus.dev"
export GEITUS_DEV_ADMIN_PASSWORD="troque-esta-senha"
./mvnw spring-boot:run
```

Rodar novamente não duplica dados. Detalhes em [backend/README.md](../../backend/README.md).

## Critérios de aceite

**Backend:** login válido → 200 + token; senha incorreta → 401; usuário inexistente → 401 com a **mesma** mensagem; usuário inativo → 401; senha em BCrypt; `senha_hash` fora das respostas; JWT assinado com claims mínimos; rota protegida sem token → 401, com token válido → 200; token expirado/adulterado → 401; `/api/health` e `POST /api/auth/login` públicos; `GET /api/auth/me` autenticado; campos vazios → 400; erros sem vazamento.

**Frontend:** `/login` renderiza; valida campos obrigatórios; loading no submit; erro claro em credenciais inválidas; rotas privadas redirecionam não autenticado para `/login`; usuário autenticado acessa a área principal; token usado nas chamadas autenticadas; logout funciona.

## Limitações conhecidas

> As pendências pré-produção desta lista são rastreadas com prioridade e prazo em [`docs/technical-debt.md`](../technical-debt.md) (DT-010 a DT-013).

- **Token no `localStorage`** (frontend): decisão pragmática do MVP, exposta a XSS. Toda leitura/escrita passa por `tokenStorage.ts` para facilitar troca futura por cookie `httpOnly` + refresh.
- **Sem refresh token**: sessão dura até a expiração do JWT; um usuário inativado após a emissão continua com token válido em rotas que não recarregam o usuário (o `/me` já bloqueia inativos).
- **Swagger liberado sem gate técnico por perfil**: hoje a restrição a desenvolvimento é documental (DEC-012). **Antes de qualquer deploy de produção**, fechar o Swagger por perfil (`@Profile("dev")` ou `springdoc.*.enabled=false` fora de dev).
- **Unicidade de e-mail global** (não por empresa) nesta fase.
- **`perfil` como texto livre** (sem enum/CHECK) — apenas `ADMIN` em uso.
- Auditoria de tempo usa `TIMESTAMP` (sem timezone); reavaliar `TIMESTAMPTZ` antes dos módulos com horário/dinheiro crítico.

## Próximos passos futuros

- Fechar o Swagger por perfil antes do primeiro deploy produtivo (prioritário).
- Refresh token + estratégia de revogação. (A revalidação de sessão no boot com estado de "carregando sessão" **já foi implementada** — ver "Regras de UX".)
- Migrar token para cookie `httpOnly`.
- Enum/allow-list de `perfil` e autorização por perfil (RBAC básico).
- Recuperação de senha, rate limiting/lockout de login.
- Decidir unicidade de e-mail (global vs. por empresa) e migrar auditoria para `TIMESTAMPTZ` quando aplicável.
