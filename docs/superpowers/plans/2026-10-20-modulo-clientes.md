# Módulo Clientes — Plano de Implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Executado pelo **fluxo do CTO** (dispatch de `back-end-executor` / `front-end-executor` + revisores). Steps usam checkbox (`- [ ]`).

**Goal:** Entregar o cadastro de clientes (pessoa física) — migration V5, domínio `customer` com API `/api/clientes` por UUID público e a página `/clientes` — conforme a spec e a DEC-029.

**Architecture:** Novo pacote `com.geitus.app.customer` no mesmo desenho de `catalog` (entidade → repository → service com métodos `*ParaUsuario` → controller fino com DTOs). Os validadores de CPF/telefone migram para `shared.validation` antes, para `customer` não depender de `company`. No frontend, as máscaras/validações de documento saem da `EmpresaPage` para `lib/documentos.ts` e a feature nova vive em `features/customers/`.

**Tech Stack:** Java 21, Spring Boot 3.5, Spring Security, Flyway, PostgreSQL 16, JUnit 5 + Mockito + Testcontainers; React + TypeScript + Vite, Tailwind v4, shadcn/ui, React Hook Form + Zod, TanStack Query, Vitest + Testing Library.

**Spec:** [`docs/modules/clientes.md`](../../modules/clientes.md) · Design: [`docs/superpowers/specs/2026-10-20-modulo-clientes-design.md`](../specs/2026-10-20-modulo-clientes-design.md) · Decisão: DEC-029.

## Global Constraints

- **Migrations append-only:** V1–V4 intactas; a nova é **`V5__clientes.sql`**. `ddl-auto: validate` deve passar.
- **PK interna `BIGINT GENERATED BY DEFAULT AS IDENTITY`** (DEC-015), **nunca exposta**; **UUID público** gerado na aplicação (`UUID.randomUUID()`), `DEFAULT gen_random_uuid()` só como rede de segurança, imutável (DEC-019/029).
- **Isolamento (DEC-016):** empresa sempre resolvida do `idUsuario` do JWT; nenhum endpoint aceita `empresaId`; cliente de outra empresa → **404** idêntico a inexistente.
- **RBAC (DEC-029):** GET/POST/PATCH de dados → qualquer autenticado; `PATCH /{id}/inativar` e `/{id}/reativar` → **ADMIN** (403 para OPERADOR).
- **Conflito (DEC-026):** CPF duplicado na empresa → **409**.
- **Normalização:** `trim`; vazio → `NULL`; CPF/telefone/WhatsApp só dígitos; `telefoneEWhatsapp = true` (ou ausente) ⇒ `whatsapp` gravado `NULL`.
- **Tamanhos:** `nome` 150, `cpf` 11, `telefone`/`whatsapp` 20, `observacoes` 500.
- **CPF é dado pessoal:** nunca em log.
- **Sem paginação** (DT-020). Sem PJ, endereço, e-mail, nascimento.
- **Git:** commits pequenos em pt-BR, padrão `tipo(escopo): descrição`, com a linha `Co-Authored-By` da sessão; trabalho integrado na `develop`.
- **Revisores obrigatórios:** `data-reviewer` ao fim da Task 2; `security-reviewer` ao fim da Task 4.

## Review Focus

1. **CPF digitado com máscara e já cadastrado sem máscara** (`111.444.777-35` vs `11144477735`) → deve dar **409**, não passar como CPF novo (normalizar **antes** de checar unicidade). → teste na Task 3.
2. **Editar cliente que tinha WhatsApp próprio e marcar "é WhatsApp"** → a coluna `whatsapp` vira `NULL` (senão o CHECK do banco estoura e o usuário vê um 409 genérico sem sentido). → testes nas Tasks 2 e 3.
3. **Busca com máscara** (`(11) 98765`) → encontra o cliente pelo telefone `11987654321`. → teste na Task 2 (query) e Task 3 (montagem do termo).
4. **Busca com `%` ou `_`** → tratados como texto literal, não curinga. → teste na Task 2.
5. **Limpar o CPF na edição** (campo apagado) → grava `NULL`, e dois clientes sem CPF não conflitam. → testes nas Tasks 2 e 3.
