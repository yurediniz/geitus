# Fase A — Categorias e Unidades de medida — Plano de Implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Executado pelo **fluxo do CTO** (`back-end-executor` / `front-end-executor` + revisores). Steps usam checkbox (`- [ ]`).

**Goal:** Criar os cadastros de Unidades de medida e Categorias (árvore) por empresa, migrar os textos atuais de `produtos.unidade`/`produtos.categoria` para FKs sem perder dados e passar o produto e suas telas a usá-los.

**Architecture:** Dois subpacotes novos em `catalog` (`catalog.unidade`, `catalog.categoria`), cada um com entidade → repository → service (`*ParaUsuario`) → controller fino → DTOs, no molde de `customer`. A árvore de categorias é um objeto de domínio puro (`CategoriaArvore`) montado em memória a partir da lista da empresa. Uma única migration aditiva (V6) cria as tabelas, semeia unidades, converte os textos e adiciona as FKs, preservando as colunas antigas. No frontend, a área de Produtos ganha sub-navegação (Produtos · Categorias · Unidades) e o formulário passa a usar selects/combobox.

**Tech Stack:** Java 21, Spring Boot 3.5, Flyway, PostgreSQL 16, JUnit 5 + Mockito + Testcontainers; React 19 + TS, Tailwind v4, shadcn/ui sobre `radix-ui` (já instalado: Popover, Dialog), RHF + Zod, TanStack Query, Vitest.

**Spec:** [`docs/modules/categorias-e-unidades.md`](../../modules/categorias-e-unidades.md) · DEC-030/DEC-031 · Design: [`../specs/2026-10-20-produtos-fase-a-design.md`](../specs/2026-10-20-produtos-fase-a-design.md)

## Global Constraints

- **Migration nova: `V6__catalogo_unidades_categorias.sql`**, aditiva; V1–V5 intactas; `produtos.categoria` e `produtos.unidade` **preservadas** (não lidas nem escritas pela aplicação a partir desta fase; removidas na Fase B).
- PK `BIGINT GENERATED BY DEFAULT AS IDENTITY` interna nunca exposta; **UUID público** gerado na aplicação, com `DEFAULT gen_random_uuid()` de segurança (DEC-019/029). Produto continua com id numérico (retrofit fora do escopo).
- Isolamento por empresa (DEC-016): empresa sempre do JWT; unidade/categoria/pai de outra empresa → **404**.
- **RBAC:** leitura (GET) livre a autenticados; escrita (POST/PATCH/DELETE) em `/api/unidades/**` e `/api/categorias/**` → **ADMIN** (matcher sem método, como em Clientes). Produtos inalterado (DEC-025).
- Conflito de unicidade/uso → **409**; regra violada (ciclo, fator) → **400**; não encontrado → **404**.
- Unidades padrão (sigla, descrição, fracionada): `UN Unidade false`, `KG Quilograma true`, `G Grama true`, `L Litro true`, `ML Mililitro true`, `M Metro true`, `CX Caixa false`, `PCT Pacote false`, `DZ Dúzia false`, `FD Fardo false`.
- Separador de caminho de categoria: `" › "` (espaço, U+203A, espaço).
- Mensagens fixas (copiar literal):
  - unidade em uso: `"Esta unidade está em uso por {N} produto(s). Inative-a para que não apareça em novos cadastros."`
  - ciclo: `"Uma categoria não pode ficar dentro dela mesma ou de uma subcategoria sua."`
  - exclusão de categoria: `"Não é possível excluir: há {S} subcategoria(s) e {P} produto(s) nesta categoria. Mova-os ou inative a categoria."` (omitir a parte zerada: `"há 2 subcategoria(s) nesta categoria"` / `"há 5 produto(s) nesta categoria"`)
  - nome repetido entre irmãos: `"Já existe uma categoria com este nome neste nível."`
  - sigla repetida: `"Já existe uma unidade com esta sigla."`
- Sem dependência nova (backend e frontend). Commits pequenos em pt-BR com `Co-Authored-By`.
- Revisores obrigatórios: `data-reviewer` (Task 1, Task 3) e `security-reviewer` (Task 3).

## Review Focus

1. **Texto de unidade com acento/caixa/espaço misturados** (" kg ", "Kg", "KILO", "pç") → todos caem na mesma unidade padrão; nenhum produto fica sem unidade. → testes na Task 1.
2. **Mesma categoria escrita de formas diferentes** ("Mercearia", "mercearia ", "MERCEARIA") → **uma** categoria raiz com o nome do primeiro produto; todos os produtos vinculados. → Task 1.
3. **Mover categoria para um neto** (ciclo indireto) → 400, árvore intacta; e mover para a raiz quando já existe raiz com o mesmo nome → 409. → Task 2.
4. **Editar produto cuja unidade/categoria foi inativada sem trocá-la** → salva normalmente; trocar para outra inativa → 400. → Task 3 (backend) e Task 6 (select mostra a atual mesmo inativa).
5. **Excluir unidade usada só como unidade de compra** → 409 (não só a de venda). → Task 2.
